# Synthetic SOC Alert Dataset Documentation
## Microsoft Innovate 2026 — Problem Statement #25: "3,000 Alerts, One Analyst"

---

### 1. Executive Summary & Why This Dataset Exists

In modern Managed Security Service Providers (MSSPs) and enterprise Security Operations Centers (SOCs), a single Tier-1 analyst is routinely inundated with thousands of security alerts per 8-hour shift. The overwhelming majority (>95%) of these alerts are false positives or routine operational noise generated by vulnerability scanners, IT management tools, software updates, and benign user actions.

Public intrusion detection datasets such as CICIDS2017, NSL-KDD, and UNSW-NB15 were designed for low-level packet-level network intrusion detection rather than modern SOC SIEM/EDR alert triage. They lack entity attributes crucial to an analyst's decision-making process: **asset criticality**, **user identities**, **process lineage**, **command-line evidence**, **MITRE ATT&CK mapping**, and **temporal progression of multi-stage cyber campaigns**.

This synthetic dataset was engineered specifically to demonstrate and benchmark the end-to-end workflow mandated by **Microsoft Problem Statement #25**:
```
3,000 Raw Heterogeneous Alerts
  │
  ▼
1. Normalize Telemetry Schema (19 structured attributes)
  │
  ▼
2. Correlate Related Alerts into Unified Incidents (DSU Graph Clustering)
  │
  ▼
3. Rank & Prioritize by Risk and Asset Criticality (Not alert volume alone)
  │
  ▼
4. Map Evidence to MITRE ATT&CK Framework (Technique & Tactic grounding)
  │
  ▼
5. Generate AI Shift-Handover Briefs (Contextual summarization with citations)
  │
  ▼
6. Human-in-the-Loop Analyst Verification (One-click triage & confirmation)
  │
  ▼
7. Mean-Time-to-Triage (MTTT) Measurement (Simulated baseline vs. empirical trials)
```

### 3. Realistic 19-Field Alert Schema

Every alert conforms to a unified schema with 19 structured fields:

| Field | Type | Description | Example |
| :--- | :--- | :--- | :--- |
| `alert_id` | `str` | Globally unique alert identifier | `"ALT-10001"` |
| `timestamp` | `str` (ISO-8601) | Exact event timestamp with timezone | `"2026-09-18T06:15:32+00:00"` |
| `source` | `str` | Originating security telemetry sensor | `"Endpoint EDR"`, `"Network Firewall"`, `"Identity Provider"` |
| `alert_type` | `str` | Specific threat or event taxonomy | `"LSASS Memory Dump"`, `"Routine Vulnerability Scan"` |
| `severity` | `str` | Raw sensor severity score | `"Critical"`, `"High"`, `"Medium"`, `"Low"`, `"Informational"` |
| `asset_id` | `str` | Asset inventory identifier | `"AST-DC-01"`, `"AST-WKSTN-FIN-042"` |
| `asset_name` | `str` | Hostname / FQDN of the affected device | `"DC-PROD-01"`, `"WKSTN-FIN-042"` |
| `asset_criticality` | `str` | Business impact tier of the target asset | `"Critical"`, `"High"`, `"Medium"`, `"Low"` |
| `user` | `str` | Associated user identity / service account | `"sarah.chen@contoso.com"`, `"svc-backup-admin"` |
| `source_ip` | `str` | Source IPv4 address | `"10.0.4.42"`, `"198.51.100.23"` |
| `destination_ip` | `str` | Destination IPv4 address | `"10.0.1.10"`, `"13.107.6.152"` |
| `protocol` | `str` | Network or local communication protocol | `"TCP"`, `"HTTPS"`, `"SMB"`, `"SSH"`, `"LOCAL"` |
| `indicator` | `str` | Key threat indicator or targeted artifact | `"vssadmin.exe"`, `"185.220.101.5"`, `"mega.nz"` |
| `description` | `str` | Human-readable explanation of the alert | `"Procdump invoked with PROCESS_ALL_ACCESS against lsass.exe"` |
| `mitre_tactic` | `Optional[str]` | Grounded MITRE ATT&CK Tactic | `"Credential Access"`, `"Initial Access"`, `"Impact"` |
| `mitre_technique` | `Optional[str]` | Grounded MITRE ATT&CK Technique ID | `"T1003.001"`, `"T1490"`, `"T1566.001"` |
| `scenario_id` | `Optional[str]` | *Evaluation Only*: Scenario grouping key | `"SCN-001"`, `"SCN-004"` |
| `ground_truth_incident_id` | `Optional[str]` | *Evaluation Only*: Ground-truth incident ID | `"GT-INC-001"`, `"GT-INC-004"` |
| `is_false_positive` | `bool` | *Evaluation Only*: Benign noise flag | `False` (Attack), `True` (Routine Noise) |

### 5. Benign Noise & False-Positive Distribution

The dataset reflects the true noise profile of an enterprise SOC, containing **2,904 benign false-positive alerts (96.8% noise rate)**:
- **Scheduled Vulnerability Scans**: Qualys/Nessus policy scans sweeping internal subnets (`Informational`, `Low`).
- **Software Distribution & Patching**: Microsoft System Center Configuration Manager (SCCM / CcmExec) deployments (`Informational`).
- **Self-Service Password Resets**: Microsoft Authenticator MFA verifications and domain password renewals (`Low`).
- **Antivirus Updates**: Microsoft Defender signature engine synchronization (`Informational`).
- **Benign CDN Queries**: Workstation DNS lookups resolving `windowsupdate.microsoft.com` (`Informational`).
- **Automated Backups**: Veeam nightly snapshot jobs backing up database storage vaults (`Low`, `Medium`).
- **SSL Expiration Warnings**: Routine staging server certificate renewals (`Low`).
- **Routine Diagnostics**: Enterprise hardware telemetry diagnostic runs (`Informational`).

**Interleaving Strategy**: Rather than placing false positives in a single block, noise alerts are uniformly interspersed across the 24-hour simulation window alongside genuine attack alerts.

### 7. Ground Truth & Strict Evaluation Safety

To prevent data leakage and guarantee scientific validity:

```
+-------------------------------------------------------------------------+
|                         RAW TELEMETRY STREAM                            |
|                                                                         |
|  [Production Telemetry Features]             [Evaluation-Only Labels]   |
|  - alert_id, timestamp, source               - scenario_id              |
|  - alert_type, severity                      - ground_truth_incident_id |
|  - asset_id, asset_name, criticality         - is_false_positive        |
|  - user, source_ip, destination_ip                                      |
|  - protocol, indicator, description, evidence                           |
+------------------------------------+------------------------------------+
                                     |
             +-----------------------+-----------------------+
             |                                               |
             ▼                                               ▼
+-------------------------+                     +-------------------------+
|   PRODUCTION PIPELINE   |                     |    OFFLINE EVALUATION   |
|                         |                     |                         |
| - Correlation Engine    |                     | - Compare predicted     |
| - Prioritization Engine |                     |   incidents to GT       |
| - AI Shift Briefer      |                     | - Compute Precision,    |
|                         |                     |   Recall, F1            |
| (Zero access to GT!)    |                     | (Evaluated post-triage) |
+-------------------------+                     +-------------------------+
```

1. **Correlation Engine Isolation**: [`backend/correlation.py`](file:///C:/Users/ASHMIT/Desktop/MICROSOFT%20WINNER/backend/correlation.py) employs Disjoint-Set Union (DSU) graph clustering relying **only** on observable telemetry: shared hostnames, user identities, threat IP indicators, and temporal proximity.
2. **Machine Learning Feature Isolation**: The feature extraction preprocessor in [`backend/ml/preprocessing.py`](file:///C:/Users/ASHMIT/Desktop/MICROSOFT%20WINNER/backend/ml/preprocessing.py) explicitly excludes `ground_truth_incident_id`, `scenario_id`, and `is_false_positive`.

### 8. Evidence-Grounded MITRE ATT&CK Mapping

In compliance with Requirement 8, MITRE ATT&CK techniques are mapped **strictly when concrete evidence is present in alert telemetry**. Routine noise alerts carry `None` for tactic and technique.

Syntax and grounding rules enforced:
- **Tactic**: Must match recognized MITRE Enterprise Matrix tactics (`Initial Access`, `Execution`, `Persistence`, `Privilege Escalation`, `Defense Evasion`, `Credential Access`, `Discovery`, `Lateral Movement`, `Collection`, `Command and Control`, `Exfiltration`, `Impact`).
- **Technique ID**: Must strictly match the canonical regular expression `^T\d{4}(\.\d{3})?$` (e.g. `T1490`, `T1003.001`).

### 11. Known Limitations & Boundaries

1. **Synthetic Nature**: All entities (`contoso.com`, IP addresses, users, file names) are synthetic and do not reflect any real-world enterprise or individual.
2. **Time Window**: The default simulation covers a 24-hour timeline. While the generator can be configured for multi-day streams, the default is optimized for shift-handover workflows.
3. **Local Evaluation Scope**: Ground truth labels are intentionally stripped from the production pipeline to model a true blind SOC environment.
